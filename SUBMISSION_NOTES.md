## SUBMISSION NOTES

## Technical Choice

## Frontend

I chose Flutter and Dart for the frontend because Flutter provides a single codebase for a responsive application across mobile and web. The frontend is separated into screens, reusable widgets, models, services, and state-management logic. API communication is kept outside the UI layer through the ticket API service.

The API base URL is configurable using --dart-define, allowing the same frontend code to communicate with either the local FastAPI server or the deployed API without changing source code.

## Backened

I chose FastAPI because it provides a lightweight REST API framework with request validation and automatic Swagger/OpenAPI documentation.

Pydantic schemas are used for request and response validation, while SQLAlchemy is used for database access.

The backend follows a layered structure:

Routes handle HTTP requests.

Schemas define and validate API data.

Services contain business and database operations.

Models define database tables.

Database configuration manages SQLAlchemy sessions.

## Database

SQLite is used as the default local-development database so the application can run without a local PostgreSQL installation.

PostgreSQL is used for the deployed environment to provide persistent relational storage.

Alembic is used for database migrations so the schema can be created and updated consistently.

## API Design

The application uses three main ticket endpoints:

POST /api/tickets - create a ticket

GET /api/tickets - list/search/filter/sort/paginate tickets and return summary counts

PATCH /api/tickets/{ticket_id} - update ticket status and priority

The GET endpoint handles search, filtering, sorting, and pagination on the backend, as required by the assignment.

The summary counts are calculated across the complete dataset and are not affected by active filters or pagination.

I intentionally did not add a separate GET-by-ID endpoint because the list API returns complete ticket objects. The selected ticket can therefore be opened directly from data already returned by the list request.

## Assumptions

A newly created ticket starts with status Open.

Only status and priority are editable after ticket creation.

Title, description, and customer email are required.

Ticket title is limited to 120 characters.

Default page size is 10 tickets.

Search applies to ticket title and customer email.

Creation and update timestamps are generated by the backend.

Summary counts represent the entire dataset, not the filtered result.

Authentication was not implemented because it was not part of the assignment requirements.

## Known Limitations

The deployed demo uses a free-tier hosting environment, so the backend may take longer to respond after inactivity.

The deployed PostgreSQL database is intended for assignment/demo use rather than long-term production.

Authentication and authorization are not implemented.

Ticket deletion, comments, attachments, file uploads, and user accounts are outside the requested scope.

Backend automated test coverage is limited; core API behavior was manually tested through FastAPI Swagger and the Flutter application.

Production features such as advanced logging, monitoring, and role-based access were outside the assignment scope.
